NumPy can multiply two 1024×1024 float32 matrices on a quad-core Intel CPU in roughly 8ms. That works out to \~250 GFLOP/s, or about 18 FLOPs per core per clock cycle at 3.4 GHz. For a CPU released in 2015, that's remarkable. It comes from decades of hand-tuned assembly in libraries like Intel MKL and OpenBLAS.

I kept wondering how far you can get starting from a plain nested for-loop in C++. I wasn't trying to beat BLAS (OpenBLAS's SGEMM is \~7,000 lines of hand-written x86 assembly). I wanted to understand *why* the gap exists and which techniques close it. This is the CPU companion to my CUDA SGEMM post: the same algorithm and the same layered optimizations, on different hardware.

Spoiler: I end up at \~9 FLOPs/core/cycle (half of peak) using cache-aware loop ordering, tiling, and OpenMP multithreading. The final kernel only works for fixed matrix sizes and makes no attempt to generalize. I wasn't building a library. I wanted a working mental model of how the CPU memory hierarchy interacts with compute.

## FLOPs and Arithmetic Intensity

For square matrices of size N×N, computing C = A×B takes one dot product per output element, and each dot product is N multiply-accumulates. That's N² output entries × N inner multiplications × 2 FLOPs (mul + add) = 2N³ FLOPs.

<Figure

  alt="Basic matrix multiplication diagram"
  caption="Matrix multiplication: each output entry requires a dot product of a row and a column."
  invert
/>

For N=1024 that's 2 × 1024³ ≈ 2.1 billion FLOPs. The three 1024×1024 float32 matrices take 3 × 4MB = 12MB. Arithmetic intensity is 2N³ / (3 × 4 × N²) ≈ N/6 ≈ 170 FLOP/byte for N=1024. With L3 bandwidth of \~40 GB/s and peak compute of \~250 GFLOP/s, this size is well into compute-bound territory. Once the data is in cache and you stop thrashing it, the limit is FP throughput, not memory.

```python
def MMM(A, B):
    C = np.zeros((A.n_rows, B.n_columns))
    for row in range(A.n_rows):
        for col in range(B.n_columns):
            for inner in range(A.n_inner):
                C[row, col] = C[row, col] + A[row, inner] * B[inner, col]
    return C
```

## Benchmarking the Baseline: NumPy on Haswell

```python
x = np.random.randn(1024, 1024).astype(np.float32)
y = np.random.randn(1024, 1024).astype(np.float32)
start = time.time_ns()
z = np.dot(x, y)
end = time.time_ns() - start
```

On an Intel i7-6700 Haswell (quad-core, 3.4 GHz), this takes \~8ms. 2.1B FLOPs in 8ms = 263 GFLOP/s = 18.5 FLOPs/core/cycle, on silicon from 2015. Here NumPy dispatches to Intel MKL's SGEMM kernel, the BLAS routine for single-precision general matrix multiply: C = α·A·B + β·C.

Where does 18.5 FLOPs/core/cycle come from? The theoretical peak for Haswell with AVX2 and FMA is 2 × (256/32) = 16 FLOPs per VFMADD instruction, at 2 instructions/cycle = 32 FLOPs/cycle. MKL gets 18.5/32 ≈ 58% of peak, which is excellent for a general-purpose BLAS on arbitrary matrices. I'll aim for half of that.

## SIMD and FMA: Where 18 FLOPs/Cycle Comes From

A scalar float multiply occupies one execution unit for one clock. A 256-bit AVX2 YMM register holds 8 floats, though, so a VMULPS (vectorized multiply) does 8 multiplications in the same slot. That's 8× the throughput per instruction. The silicon is already there; you just have to get the compiler to use it.

<Figure
  src="/cpu-mmm/Scalar_vs_Vectorized.webp"
  alt="Scalar vs vectorized operations comparison"
  caption="SIMD: one instruction, multiple data. AVX2 processes 8 floats per operation."
  invert
/>

FMA (Fused Multiply-Add) combines a multiply and an add into one instruction: A += B \* C. On Haswell, VFMADD213PS operates on three 256-bit YMM registers and performs 8 fused multiply-adds (16 FLOPs) in one instruction. According to Agner Fog's tables, VFMADD has a throughput of 0.5 cycles on Haswell, because two execution ports can handle it. So the theoretical peak is 2 VFMADD/cycle × 16 FLOP/VFMADD = 32 FLOP/cycle per core.

VFMADD also has a latency of 5 cycles, so its result isn't available as input to the next FMA for 5 cycles. Sustaining 2 FMAs/cycle through that 5-cycle latency takes at least 5 × 2 = 10 independent FMAs in flight at once, or 160 FLOPs of in-flight work. This is where instruction-level parallelism (ILP) comes in. The inner loop has to be structured so the compiler can issue several independent FMAs without waiting on data dependencies. That's why the MKL SGEMM kernel uses multiple accumulator registers: each holds an independent partial sum, which breaks the dependency chain.

## Starting from Scratch: Naive C++

Target hardware: Intel i7-6700, quad-core Haswell @ 3.4GHz. Cache layout: 32KiB L1d per core, 256KiB L2 per core, 8MB shared L3. Compiler: clang 14.0 with -O3 -march=native -ffast-math. Benchmarking via Google Benchmark; every variant validated against PyTorch's output for numerical correctness.

The target is \~9 FLOPs/core/cycle, roughly half of the theoretical peak. That isn't competitive with BLAS (which gets 18), but it's far above a naive implementation. The kernel only works for fixed matrix sizes known at compile time (template parameters). I'm giving up generality for speed on purpose.

Here's the starting point, the most straightforward version you'd write:

```cpp
template <int rows, int columns, int inners>
inline void matmulImplNaive(const float *left, const float *right,
                            float *result) {
  for (int row = 0; row < rows; row++) {
    for (int col = 0; col < columns; col++) {
      for (int inner = 0; inner < inners; inner++) {
        result[row * columns + col] +=
            left[row * columns + inner] * right[inner * columns + col];
      }
    }
  }
}
```

Without optimization flags it takes 4.4s. With -O3 -march=native -ffast-math it takes 1.6s, a 2.75× speedup from the compiler alone, which is a good reminder of how much the compiler does. But 1.6s is still \~20× slower than NumPy. A small first improvement is to accumulate the dot product in a local variable and write it to C once at the end:

```cpp
template <int rows, int columns, int inners>
inline void matmulImplNaiveRegisterAcc(const float *left, const float *right,
                                       float *result) {
  for (int row = 0; row < rows; row++) {
    for (int col = 0; col < columns; col++) {
      float acc = 0.0;
      for (int inner = 0; inner < inners; inner++) {
        acc += left[row * columns + inner] * right[inner * columns + col];
      }
      result[row * columns + col] = acc;
    }
  }
}
```

That gets it down to 1.5s. Without the explicit accumulator, the compiler has to prove it's safe to keep partial sums in a register instead of writing them to `result[]` on every iteration, and pointer aliasing can prevent that. Making it explicit removes the ambiguity. We're still nowhere near BLAS, and the next bottleneck is the memory access pattern.

## Cache-Aware Loop Ordering

C and most systems languages use row-major storage: matrix elements are laid out row by row in memory. A\[i]\[j] and A\[i]\[j+1] are adjacent. A\[i]\[j] and A\[i+1]\[j] are N floats apart.

<Figure
  src="/cpu-mmm/stride_matrix_representation.webp"
  alt="Strided matrix memory layout"
  caption="Row-major memory layout: rows are contiguous, columns are strided by N×4 bytes."
  invert
/>

In the naive row-col-inner loop order, the innermost loop walks across a row of A, which is sequential and cache-friendly, but down a *column* of B, which has stride N. For N=1024 with float32, each step down a column of B jumps 4KB. A full column traversal touches 1024 × 4KB = 4MB, and L1d is only 32KB, so every access to B in the inner loop misses the cache. That's why the naive version is so slow. It's memory-bound even though the problem has plenty of arithmetic intensity.

<Figure
  src="/cpu-mmm/cache-unaware-dot-product.webp"
  alt="Cache-unfriendly access pattern for matrix B"
  caption="The naive loop order walks B column by column, so every inner step is a cache miss."
  invert
/>

The fix is to swap the col and inner loops, so the inner index advances in the middle loop and the columns are walked in the innermost one:

```cpp
template <int rows, int columns, int inners>
inline void matmulImplLoopOrder(const float *left, const float *right,
                                float *result) {
  for (int row = 0; row < rows; row++) {
    for (int inner = 0; inner < inners; inner++) {
      for (int col = 0; col < columns; col++) {
        result[row * columns + col] +=
            left[row * columns + inner] * right[inner * columns + col];
      }
    }
  }
}
```

<Figure
  src="/cpu-mmm/cache-aware-dot-prod-reorder-loops.webp"
  alt="Optimized cache-aware access pattern after loop reordering"
  caption="After loop reordering: the inner loop traverses B and C sequentially, which is cache-line friendly and vectorizable."
  invert
/>

Runtime: 89ms. A one-line loop swap gives a 17× speedup, the biggest single win in this post. The inner loop now walks rows of B and C sequentially, so every cache miss brings in 16 useful floats, and the predictable pattern lets the hardware prefetcher help. It also lets the compiler auto-vectorize. The sequential access is what allows it to emit VFMADD instructions:

```asm
; Broadcast a single fp32 from row of A to all 8 entries of ymm0
; vbroadcastss ymm0, dword ptr [rsi + 4*r8]

; Load 8 entries from current row of B into ymm registers
vmovups ymm1, ymmword ptr [rbx + 4*rbp - 96]
vmovups ymm2, ymmword ptr [rbx + 4*rbp - 64]
vmovups ymm3, ymmword ptr [rbx + 4*rbp - 32]
vmovups ymm4, ymmword ptr [rbx + 4*rbp]
; Multiply current entry of A (ymm0) times B (ymm1-4), add partial results from C
vfmadd213ps ymm1, ymm0, ymmword ptr [rcx + 4*rbp - 96]
vfmadd213ps ymm2, ymm0, ymmword ptr [rcx + 4*rbp - 64]
vfmadd213ps ymm3, ymm0, ymmword ptr [rcx + 4*rbp - 32]
vfmadd213ps ymm4, ymm0, ymmword ptr [rcx + 4*rbp]
; Store partial results back to C
vmovups ymmword ptr [rcx + 4*rbp - 96], ymm1
vmovups ymmword ptr [rcx + 4*rbp - 64], ymm2
vmovups ymmword ptr [rcx + 4*rbp - 32], ymm3
vmovups ymmword ptr [rcx + 4*rbp], ymm4
```

## Tiling

Loop reordering fixed one cache problem and exposed another. In the reordered version, the middle loop (over `inner`) scans through full rows of B, and for a 1024×1024 matrix a full row is 4KB. By the time the outer `row` loop increments and the `inner` loop starts over, the B rows we just used have been evicted from L1 (32KB). We reload the same data for every row of A, from a cold cache each time.

<Figure
  src="/cpu-mmm/Basic_tiling_inner.webp"
  alt="Cache tiling concept visualization"
  caption="Without tiling: by the time we revisit a tile of B for the next row of A, it's been evicted from cache."
  invert
/>

Tiling (also called cache blocking) fixes this by splitting the middle loop into an outer tile loop and an inner tile loop. The tile loop handles a chunk of the `inner` dimension that fits in L1 before moving to the next chunk. Within each tile we process many rows of A, so the tile of B stays in cache across all of them:

```python
def matmulImplTiling(left, right, result):
    # iteration 1
    for row in range(6):
        for inner in range(3):
            for column in range(6):
                result[row, column] += left[row, inner] * right[inner, column]

    # iteration 2
    for row in range(6):
        for inner in range(3, 6):
            for column in range(6):
                result[row, column] += left[row, inner] * right[inner, column]
```

<Figure
  src="/cpu-mmm/Tiling_on_inner.webp"
  alt="Tiling visualization with block boxes and colored arrows"
  caption="Tiling: the colored arrows show that the same tile of B is reused across multiple rows of A before eviction."
  invert
/>

```cpp
template <int rows, int columns, int inners, int tileSize>
inline void matmulImplTiling(const float *left, const float *right,
                             float *result) {
  for (int innerTile = 0; innerTile < inners; innerTile += tileSize) {
    for (int row = 0; row < rows; row++) {
      int innerTileEnd = std::min(inners, innerTile + tileSize);
      for (int inner = innerTile; inner < innerTileEnd; inner++) {
        for (int column = 0; column < columns; column++) {
          result[row * columns + column] +=
              left[row * inners + inner] * right[inner * columns + column];
        }
      }
    }
  }
}
```

With a tile size of 16, runtime drops to 70ms, another 21% over the loop-reordering version. Working from L1 capacity alone, the 'optimal' tile size comes out to \~3.5 (just enough rows of B to fit in 32KB), but a grid search found 16 to be faster. I attribute the difference to loop overhead, the hardware prefetcher doing better with larger strides, and L2 reuse: data evicted from L1 into L2 can still be warm when it's accessed again.

## Multi-Dimensional Tiling

So far only the `inner` dimension is tiled, but `rows` and `columns` can be tiled too. Each extra tiled dimension shrinks the working set so it fits in a closer cache level, at the cost of more loop overhead. For 1024×1024 matrices, tiling all three dimensions gives diminishing returns, because the data is small enough that L3 absorbs most of the traffic anyway. For larger matrices (say 8192×8192) multi-level tiling becomes necessary. Without it, the B tile you kept in L1 gets pushed out to L3 before the next row of A even starts.

<Figure

This maps directly onto CUDA SGEMM. Blocktiling plays the role of L3 tiling (GMEM → SMEM), and threadtiling plays the role of L1 tiling (SMEM → registers). On the CPU you write 'tileSize=16' in a loop, while CUDA makes you manage the shared memory buffer yourself. It's the same idea with more manual control.

## Multithreading with OpenMP

The i7-6700 has 4 physical cores with hyperthreading, for 8 logical cores, and so far we've used one. OpenMP makes the syntax easy, but you still need to think about data dependencies before putting a `#pragma omp parallel for` on the outermost loop.

<Figure
  src="/cpu-mmm/tiled_MMM_dependecies.webp"
  alt="Thread dependency partitioning for matrix multiplication"
  caption="Dependency structure: C[i][j] depends only on row i of A and column j of B, with no dependencies between outputs."
  invert
/>

Different output tiles C\[rowTile]\[colTile] have no write dependencies between them, since each thread writes to its own region of C. So I partition C into (rows/256) × (cols/256) chunks and give each chunk to a thread. Threads read A and B (shared and read-only) and write to non-overlapping parts of C, so no synchronization is needed.

<Figure
  src="/cpu-mmm/Thread_partitioning.webp"
  alt="Work distribution across threads"
  caption="Partitioning C into 16 chunks (4×4 blocks) assigned to 8 hyperthreads, roughly 2 chunks per thread."
  invert
/>

```cpp
template <int rows, int columns, int inners,
          int tileSize = ROW_COL_PARALLEL_INNER_TILING_TILE_SIZE>
inline void matmulImplRowColParallelInnerTiling(const float *left,
                                                const float *right,
                                                float *result) {
#pragma omp parallel for shared(result, left, right) default(none) \
  collapse(2) num_threads(8)
  for (int rowTile = 0; rowTile < rows; rowTile += 256) {
    for (int columnTile = 0; columnTile < columns; columnTile += 256) {
      for (int innerTile = 0; innerTile < inners; innerTile += tileSize) {
        for (int row = rowTile; row < rowTile + 256; row++) {
          int innerTileEnd = std::min(inners, innerTile + tileSize);
          for (int inner = innerTile; inner < innerTileEnd; inner++) {
            for (int col = columnTile; col < columnTile + 256; col++) {
              result[row * columns + col] +=
                  left[row * inners + inner] * right[inner * columns + col];
            }
          }
        }
      }
    }
  }
}
```

With 8 threads (collapse(2) across the rowTile and columnTile loops), runtime drops to \~16ms. A 5.5× speedup from 8 threads is reasonable, given that hyperthreads share physical execution units. The full path from naive to final was 4400ms → 89ms → 70ms → 16ms. That's about 5× slower than NumPy/MKL at 8ms. The remaining gap is register tiling (MKL manages accumulator registers across several output rows at once), better loop unrolling, and handwritten SIMD that the compiler doesn't find.

## Conclusion

CPU SGEMM and GPU SGEMM are the same algorithm on different hardware. Both come down to managing a three-level memory hierarchy to keep the compute units fed: L1/L2/L3 caches on the CPU, registers/SMEM/GMEM on the GPU. The tiling patterns are the same. CUDA just makes you write them out yourself instead of leaving them to the compiler.

What surprised me most was that a single loop-order swap (naive → cache-aware) gave a 17× speedup with no change to the algorithm. The naive version wasn't compute-bound, or even especially bandwidth-bound in absolute terms. It was *cache-thrashing* constantly, leaving the execution units stalled on DRAM. A lot of performance work turns out to be about waiting less for data. What helps is sequential access, reuse, and access patterns the hardware prefetcher can follow.

The gap to production BLAS (\~5× here) comes from things I didn't implement: register-level tiling (several independent FMA accumulators to exploit ILP), hand-tuned SIMD intrinsics for the inner kernel, and multi-level tiling calibrated to each cache level. OpenBLAS's SGEMM kernel is 7,000 lines of x86 assembly for a reason. I got about 50% of theoretical peak, and BLAS gets \~56%. That last margin represents years of engineering.

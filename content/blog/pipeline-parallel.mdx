At some point a model stops fitting in a single GPU's memory, and you have to split it across several. BLOOM, Huggingface's 175B parameter Transformer, needs \~350GB just to store its weights in bfloat16, and an A100 80GB holds roughly a quarter of that. Training it on 384 GPUs meant spreading different layers across machines, a technique called model partitioning or pipeline parallelism.

The naive version uses GPUs very poorly. If GPU2 can't start until GPU1 finishes, you've serialized compute across machines that are supposed to run in parallel. This post walks through three approaches (naive, GPipe, and PipeDream) and the tradeoffs between GPU utilization, memory use, and mathematical equivalence to single-GPU training. I'll also point out the parts that didn't click for me until I traced through the scheduling logic by hand.

## Naive Model Parallelism

The most straightforward implementation splits the model's layers into contiguous groups, assigns each group to a GPU, and trains one minibatch at a time. Take a 4-layer model split across 2 GPUs. GPU1 runs layers L1–L2, produces the intermediate activation tensor, and MPI-sends it to GPU2. GPU2 runs L3–L4, computes the loss, and starts the backward pass. At the L2→L3 boundary going backward, GPU2 sends its input gradients to GPU1, which finishes backprop. Each GPU applies its own gradient updates locally.

This is bit-exact with single-GPU training, with the same math and the same numerics. Communication is point-to-point (MPI.Send/MPI.Recv), so there's no need for collectives like AllReduce or broadcast. The problem shows up as soon as you watch the pebble graph below:

A few things go wrong:

- GPU utilization is 1/n. At any moment exactly one GPU is computing and the rest are idle, so with 8 pipeline stages each GPU does useful work only 12.5% of the time.
- Communication and computation don't overlap. While the activation tensor is crossing the network, no GPU is doing anything useful.
- Early stages use a lot of memory. GPU1 has to cache the forward activations for the entire minibatch until the backward pass reaches it, which can mean gigabytes of intermediate tensors held for the whole forward and backward pass.

## GPipe: Microbatches and Gradient Accumulation

GPipe splits each minibatch into m equal-sized microbatches, sends them through the pipeline one after another, and accumulates gradients before the optimizer step. The math is exact. The gradient of a sum is the sum of the gradients, so adding up the microbatch gradients gives the same result as processing the full minibatch at once. This is gradient accumulation, and it's mathematically bit-equivalent to single-GPU training.

What this buys you is overlap. While GPU2 runs the forward pass for microbatch 2, GPU1 can start the forward pass for microbatch 3. With several microbatches in flight, more GPUs are busy at the same time.

### GPipe: Interleaving and Its Limits

In practice the overlap is limited. A GPU can't start on microbatch i until the previous stage has finished it and sent the output. If every stage takes the same time the pipeline runs cleanly, but there's still startup and teardown time when some GPUs have nothing to do. These idle slots are called pipeline bubbles.

### GPipe: Pipeline Bubbles

A bubble is idle time caused by a data dependency that hasn't been satisfied yet. GPU4 can't run the forward pass for microbatch 1 until GPU3 has finished it and sent the activation. In the backward pass, likewise, each stage waits for the next stage to send back its input gradient. The fraction of time lost to bubbles depends on the pipeline depth n (number of GPU stages) and the number of microbatches m:

$$
\text{bubble fraction} = 1 - \frac{m}{m + n - 1}
$$

As m → ∞, the bubble fraction → 0. In practice m ≈ 4n is a common target (bubble fraction ≈ 20%). The catch is that a larger m means a larger total batch size, which requires learning rate scaling (linear scaling rule) and increases the activation memory you have to cache. You're trading memory for utilization.

### GPipe: Memory and Gradient Checkpointing

GPipe's memory problem is severe. During the all-forward phase, the activations for all m microbatches are live at once. Each GPU has to keep a microbatch's activations from its forward pass until the matching backward pass reaches it. With m=8 microbatches on a 4-GPU pipeline, GPU1 holds 8 microbatches' worth of activations at the same time, 8× the activation memory of a single-GPU run.

GPipe handles this with gradient checkpointing (also called activation recomputation). Instead of caching every intermediate activation, it caches only the inputs at pipeline-stage boundaries and recomputes the activations during the backward pass, trading compute for memory. Without gradient checkpointing, peak memory per GPU is O(batchsize × layers_per_gpu). With it:

$$
O\left(\text{batchsize} + \frac{\#\text{total layers}}{\#\text{GPUs}} \cdot \frac{\text{batchsize}}{\#\text{microbatches}}\right)
$$

<Figure
  src="/pipeline-parallel/GPipe-gradient-checkpointing.webp"
  alt="Memory state during backward pass with gradient checkpointing"
  caption="Gradient checkpointing: only boundary inputs are cached. Activations are recomputed during backward, adding ~33% compute overhead."
  invert
/>

For large models the 33% compute overhead from recomputation is usually worth paying, since it's often the only way to fit the model in GPU memory at all. PyTorch's `torch.utils.checkpoint.checkpoint()` and Megatron-LM's activation recomputation are both GPipe-style gradient checkpointing, so if you've used either, you've used this idea.

## PipeDream: 1F1B and Earlier Backward Passes

PipeDream's observation is that you don't have to forward every microbatch before starting any backward passes. As soon as the last stage finishes the forward pass for microbatch 1, it can start the backward pass for microbatch 1, even while earlier stages are still working on microbatches 2, 3, 4... This is the 1F1B (one forward, one backward) pattern. In steady state, each GPU alternates between a forward pass for a new microbatch and a backward pass for an older one.

<Figure
  src="/pipeline-parallel/PipeDream_schedule.webp"
  alt="PipeDream schedule with 4 GPUs and 8 microbatches showing 1F1B pattern"
  caption="PipeDream 1F1B schedule: blue = forward, green = backward. Numbered by microbatch ID."
/>

This saves a lot of memory. In GPipe all m microbatches are in flight during the all-forward phase, so activation memory grows with m. In PipeDream's steady state GPU1 starts a backward as soon as it finishes a forward, so at most n microbatches (the pipeline depth) are in flight at once. For both algorithms, activation memory without gradient checkpointing is:

$$
O\left(\#\text{max microbatches in flight} \cdot \text{microbatch-size} \cdot \frac{\#\text{total layers}}{\#\text{GPUs}}\right)
$$

The two algorithms differ only in the max-microbatches-in-flight term. GPipe's all-forward phase puts all m microbatches in flight, while PipeDream's 1F1B schedule keeps at most n (the pipeline depth). You can see it in GPU1's row of the diagram: in steady state it alternates F and B and never starts a new forward without finishing a backward first.

<Figure
  src="/pipeline-parallel/Pipedream_steady_state.webp"
  alt="PipeDream steady state showing GPU1 alternating forward and backward passes"
  caption="PipeDream steady state: GPU1 alternates 1F1B after the warmup phase, keeping at most n microbatches in flight."
/>

In the example above (4 GPUs, 8 microbatches), PipeDream has at most 4 microbatches in flight and GPipe has 8, so PipeDream halves the activation memory overhead. The bubble fraction is the same for both, because it's set by the pipeline structure (n stages, m microbatches) rather than by when the backward passes start. You can check this visually. Take the PipeDream schedule, slide all the backward passes to the right until they come after the last forward, and you get GPipe. The total time is the same; only the activation memory profile changes.

### Communication Volume: Pipeline vs Data Parallelism

For a model with dense layers of hidden dimension N, each pipeline stage boundary sends activations of size (microbatch_size × N) forward and gradients of the same size backward. Total pipeline communication per minibatch is (n-1) × 2 × batchsize × N floats, which scales with pipeline depth and activation size rather than parameter count. Data parallelism (Ring AllReduce) transfers roughly 2 × (total_params / n_gpus) floats per step, which scales with model size rather than activations. So for very large models with small activations, pipeline parallelism can need less communication, and for models with large activations (vision, long-context language models) it can need more. There's one more difference that matters a lot: data-parallel AllReduce overlaps naturally with the backward pass, while pipeline-parallel point-to-point transfers sit on the critical path and are harder to hide.

## Combining Pipeline and Data Parallelism

Pipeline and data parallelism are orthogonal, so you can use both at once. In a combined setup you run several pipeline *replicas* (data parallelism across replicas), and each replica is itself a pipeline (pipeline parallelism across stages). Your effective batch size becomes (microbatch_size × n_microbatches × n_data_parallel_replicas), so the batch has to be large enough to keep both dimensions busy without tiny, noisy microbatches.

<Figure
  src="/pipeline-parallel/DP_and_PP.webp"
  alt="Illustration of orthogonal communication partners in combined data and pipeline parallelism"
  caption="Combined DP + PP: each GPU participates in two communicators: one for pipeline neighbors, one for data-parallel peers."
/>

The implementation uses MPI Communicators, which are subgroups of GPUs that only talk within the group. Each GPU belongs to two. One holds its pipeline stage peers (all GPUs with the same layer slice, for AllReduce), and the other holds its pipeline neighbors (the stages before and after, for point-to-point activations and gradients). Together they partition the cluster into a 2D grid of pipeline depth × data-parallel width. DeepSpeed, Megatron-LM, and FairScale all implement this pattern. Large training runs often add a 3rd dimension, tensor parallelism within each layer, for a 3D grid of pipeline × data × tensor.

## Implementation: GPipe in Python

Data parallelism needs AllReduce, a collective that requires every worker to coordinate. Pipeline parallelism only uses point-to-point sends and receives between adjacent stages, so each GPU can follow a simple, static schedule with no global synchronization. DeepSpeed's pipeline engine is built this way: one worker per GPU, each running a sequence of commands fixed before the minibatch starts.

```python
def minibatch_steps(self):
    yield [ZeroGrad()]

    # STAGE 1: First, we FWD all microbatches
    for microbatch_id in range(self.num_micro_batches):
        yield self.steps_FWD_microbatch(microbatch_id)

    # at this position, all microbatches are in flight and
    # memory demand is highest

    # STAGE 2: Then, we BWD all microbatches
    for microbatch_id in reversed(range(self.num_micro_batches)):
        yield from self.steps_BWD_microbatch(microbatch_id)

    # updating the weights is the last step of processing any batch
    yield [OptimizerStep()]
```

This is the GPipe schedule: all forwards first, then all backwards in reverse order. Note the comment about peak memory. Between the last FWD and the first BWD, every microbatch's activations are live at once. Here's the forward pass for one microbatch:

```python
def steps_FWD_microbatch(self, microbatch_id):
    cmds = []
    if self.is_first_stage:
        # first pipeline stage loads data from disk
        cmds.append(LoadMicroBatchInput(microbatch_id=microbatch_id))
    else:
        # all other stages receive activations from prev pipeline stage
        cmds.append(RecvActivations())

    cmds.append(Forward(microbatch_id=microbatch_id))

    if not self.is_last_stage:
        # all but the last pipeline stage send their output to next stage
        cmds.append(SendActivations())
    return cmds
```

Each stage loads input (or receives activations), runs the forward pass, and sends activations to the next stage. The backward pass mirrors this in reverse. The last stage has the loss, so it loads targets instead of receiving gradients. One detail to notice is the `BackwardGradAllReduce` on the first microbatch (which is processed last in backward order). It overlaps the gradient AllReduce with the backward computation and hides some of the data-parallel communication cost:

```python
def steps_BWD_microbatch(self, microbatch_id):
    cmds = []
    if self.is_last_stage:
        # last pipeline stage loads targets from disk
        cmds.append(LoadMicroBatchTarget(microbatch_id=microbatch_id))
    else:
        # all other stages wait to receive grad from next stage
        cmds.append(RecvOutputGrad())

    if self.is_first_microbatch(microbatch_id):
        # interleaved backprop and AllReduce during last microBatch of BWD
        cmds.append(BackwardGradAllReduce(microbatch_id=microbatch_id))
    else:
        cmds.append(BackwardGradAcc(microbatch_id=microbatch_id))

    if not self.is_first_stage:
        # all but last pipeline stage send their input grad to prev stage
        cmds.append(SendInputGrad())
    yield cmds
```

The difference between `BackwardGradAcc` and `BackwardGradAllReduce` is easy to miss. For every microbatch except the last one in backward order, gradients are accumulated locally with no synchronization across data-parallel replicas. The AllReduce happens only on the last backward, and launching it as a background NCCL operation alongside the final backprop hides part of the network round-trip latency.

## Hardware Context: Interconnects and Scaling

<Figure
  src="/pipeline-parallel/distributed-computing-hardware.webp"
  alt="Hardware hierarchy showing multi-node GPU clusters with PCIe, NVLink, InfiniBand"
  caption="Distributed training hardware: NVLink at ~900GB/s within a node; InfiniBand HDR at ~200Gbps between nodes."
  invert
/>

Bandwidth shapes how you lay out a pipeline. NVLink within a node is \~900GB/s bidirectional, fast enough that intra-node pipeline stages are almost never bandwidth-limited. Cross-node InfiniBand is 25–200Gbps depending on the generation, easily 10-100× slower. My rule of thumb is to put pipeline stage boundaries at intra-node boundaries where possible, and to use pipeline parallelism for the inter-node communication you can't avoid.

<Figure
  src="/pipeline-parallel/strong-vs-weak-scaling.webp"
  alt="Visual comparison of strong vs weak scaling strategies"
  caption="Strong vs weak scaling: strong = fixed problem size across more GPUs; weak = fixed per-GPU workload."
  invert
/>

Pipeline parallelism is a form of weak scaling for model size. Each GPU holds a fixed number of layers, and you grow the total parameter count by adding GPUs to the pipeline. Bubble overhead doesn't depend on model size, only on pipeline depth and microbatch count. That's a big part of why pipeline parallelism is standard in LLM training infrastructure: adding layers doesn't add utilization loss.

## Conclusion

In the end, pipeline parallelism is a scheduling problem. Once the model is split across GPUs, you have to decide in what order to run forward and backward passes across microbatches to get high utilization without running out of memory. Naive MP is correct but leaves most GPUs idle. GPipe recovers utilization with microbatches at the cost of much more activation memory. PipeDream's 1F1B halves that activation memory and keeps the same bubble fraction. Each improvement costs something somewhere else.

The part I find most interesting is how pipeline depth interacts with batch size. Deeper pipelines (more stages) have more bubble overhead unless you add microbatches. More microbatches mean a bigger batch, and a bigger batch means rescaling the learning rate. Eventually convergence becomes the limit, because very large batches don't generalize as well without careful warmup and decay schedules. So the scheduling algorithm and the optimizer aren't independent, and large-scale training frameworks (Megatron-LM, DeepSpeed, FairScale) have to design them together.

If you're building or debugging a multi-GPU training setup, the most common bug I've seen is broken gradient accumulation, where microbatch gradients get applied as independent updates instead of being summed before the optimizer step. I always check numerics against single-GPU training before looking at performance.

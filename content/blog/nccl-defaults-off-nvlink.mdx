In [part 1](/blog/tp-without-nvlink) I found that on GPUs without NVLink, most all-reduce time is a fixed cost paid on every call, and that crossing Ethernet adds more of it. This post is about the setting that moved that cost more than anything else I tried: which algorithm and protocol NCCL runs at each message size.

Across two PCIe boxes on Ethernet, NCCL's defaults kept the slowest reasonable protocol in exactly the size range decode lives in. The fix ended up being a rules file three lines long.

## Two choices on every call

Every collective NCCL runs comes down to two settings. The algorithm decides the route data takes between GPUs. The protocol decides how each piece of data is packaged, and how the receiver finds out it has arrived.

The two algorithms that matter here are Ring and Tree. Ring is the loop from part 1: 2(N−1) steps, and the best use of bandwidth. Tree reduces data up a tree and broadcasts the result back down. NCCL's tree is only a tree between nodes; inside each node the GPUs form a chain. Across two boxes, it crosses the slow link far fewer times in a row than Ring does, which matters when each crossing has a high fixed cost. (NCCL's newer all-reduce algorithms need NVSwitch or in-network reduction hardware, which these boxes don't have.)

<Diagram name="ring-vs-tree" caption="Every Ring step is gated by the slowest link, the Ethernet hop. Tree crosses it once on the way up and once on the way down." />

There are three protocols, and they trade fixed cost against efficiency. LL ("low latency") sends 8 bytes of data alongside 8 bytes of flags in every 16; the receiver just polls the flags, so there's no separate handshake, but half of every write is bookkeeping. LL128 packs 120 bytes of data into each 128-byte line, which only works if the hardware guarantees that a 128-byte write lands all at once, so NCCL only turns it on where it trusts that, which in practice means NVLink. Simple sends full payloads and synchronises with separate flags: the best bandwidth and the highest fixed cost.

<Diagram name="protocols" caption="What each protocol puts on the wire in one 128-byte window. The flags are how a receiver knows the data has landed." />

In terms of part 1's model, LL has a small α and a poor B, Simple has a large α and a good B, and LL128 sits in between. Small messages want LL and large ones want Simple. Everything depends on where you switch.

## How NCCL picks

For each call, NCCL estimates how long every algorithm would take under every protocol and picks the cheapest. The estimates come from built-in latency and bandwidth numbers for each kind of link: NVLink, PCIe, network. You can watch it decide:

```bash
NCCL_DEBUG=INFO NCCL_DEBUG_SUBSYS=TUNING <your command>
```

The catch is that those numbers are generic. Nothing measures your fabric. If your hop latencies or achieved bandwidths differ from what NCCL assumes, the switch points land in the wrong places.

(One sanity note for reading nccl-tests output: it reports an algorithm bandwidth, bytes over time, and a bus bandwidth, which multiplies that by 2(N−1)/N to account for the ring's traffic. Bus bandwidth is the one you can compare across GPU counts.)

## Inside one box, it's about right

On 8 GPUs in one PCIe box, NCCL moves from Ring/LL to Ring/Simple close to where the measured curves actually cross, and LL128 never wins even when forced. If you only ever use one box, the defaults are fine.

## Across Ethernet, it stays on LL far too long

Across two boxes NCCL keeps Ring/LL well into the megabyte range, because its cost model assumes LL moves data over the network faster than it actually did. So in the band where high-concurrency decode messages live, the default ends up being the slowest reasonable choice by a wide margin.

<Diagram name="chart-forced" caption="16 GPUs across two boxes over Ethernet, nccl-tests with each algorithm and protocol forced, log-log. Lower is better; NCCL's default is dashed." />

Read the chart left to right and follow whichever line is lowest, and you get three regions. For small messages it's Tree/LL, because Tree crosses the slow link fewer times; the default does use Tree, but only for the very smallest sizes. Through the middle it's Ring/LL128, which NCCL disables on these GPUs because the path between them is PCIe; forced on, it was the fastest setting in that band. For large messages everything converges on the GPU's own PCIe link and Ring/Simple wins. The bump in the dashed line is the moment the default finally gives up on LL.

There was one more oddity. Run the same Ring/LL benchmark across the two boxes several times and the results fall into two clusters: same fixed cost, different throughput. One box-to-box hop's LL sender runs at one of two speeds and stays at that speed for the life of the process. Ring/Simple on the same NICs doesn't do this. I never isolated the cause, but it's two more reasons to keep LL out of the middle band: a single launch can mislead you badly, and avoiding LL avoids the lottery.

## A rule by size, not one override

Benchmarks are one thing and serving is another, so I forced each of the seven algorithm-protocol pairs inside vLLM (TP16 across two boxes) and measured decode steps from 1 to 512 concurrent requests. The winner changed with load: the default at one request, Tree/LL at low load, Tree/LL128 in between, Ring/LL128 at high load.

That's not random. Decode message size tracks concurrency, so most of those winners line up with the size regions from nccl-tests. The fix is a rule by size rather than one global override: Tree/LL for small messages, Ring/LL128 in the middle, Ring/Simple for large.

<Diagram name="size-rule" caption="NCCL's default across Ethernet against the size rule. The difference sits right where decode messages live; the boundaries depend on your fabric." />

With that rule in place, every load matched the best forced setting, including the loads where Tree/LL128 had won, so the rule doesn't need a band for it. At one request nothing changes. At high concurrency the decode step got dramatically shorter, and throughput rose by a similar factor. Per-call time inside vLLM also matched nccl-tests for the same forced setting, for Simple and LL128 at every size. LL at megabyte sizes ran slower inside the server than in the benchmark, which is one more reason to keep it out of that band.

## Doing this on your own fabric

NCCL can load a tuner plugin that overrides the algorithm, protocol and channel count per collective and size range. I started from NVIDIA's example plugin, which reads its rules from a CSV-style file:

```csv
collective,min_bytes,max_bytes,algorithm,protocol,channels,nNodes,nRanks
allreduce,<a>,<b>,tree,ll,<ch>,2,16
allreduce,<b>,<c>,ring,ll128,<ch>,2,16
allreduce,<c>,4294967295,ring,simple,<ch>,2,16
```

The boundaries `<a>`, `<b>` and `<c>` are specific to your hardware. You can find them with a sweep like this one on any multi-node box:

```bash
# Open MPI's mpirun doesn't pass your shell environment to remote ranks,
# so forward NCCL_* with -x.
for algo in Ring Tree; do
  for proto in LL LL128 Simple; do
    NCCL_ALGO=$algo NCCL_PROTO=$proto \
      mpirun -np 16 -H <host1>:8,<host2>:8 -x NCCL_ALGO -x NCCL_PROTO \
      ./build/all_reduce_perf -b 256 -e 128M -f 2 -d bfloat16 -n 100 -w 20 \
      > sweep_${algo}_${proto}.txt
  done
done
```

Run each setting more than once if any of your ranks cross a network. Then, when you wire up the plugin, three things will bite you.

First, the example plugin has a bug: for any collective that matches no rule, it sets the channel count to 1, which silently puts small all-reduces on a single channel. Patch it to leave unmatched collectives alone.

Second, the plugin can't pick a protocol NCCL has already ruled out, and LL128 is disabled on PCIe paths, so you have to allow it as well. Scope that to all-reduce, or NCCL's own model will start using LL128 for other collectives too.

Third, a plain `NCCL_ALGO=Tree` breaks vLLM startup, because all-gather has no Tree implementation. If you're experimenting without a plugin, use the scoped form, `NCCL_ALGO=allreduce:tree`. Put together, the environment looks like this:

```bash
NCCL_PROTO=allreduce:LL,LL128,Simple
NCCL_TUNER_PLUGIN=/path/to/libnccl-tuner.so
NCCL_TUNER_CONFIG_FILE=/path/to/rules.conf
```

## Is forcing LL128 safe without NVLink?

LL128 relies on 128-byte writes arriving whole, which is exactly why NCCL turns it off on PCIe. So before shipping it I checked results, not just timings: a long soak across sizes with LL128 forced and results checked, which found zero wrong values, plus a comparison of generated text under load that showed no corruption. That's evidence for this fabric, not a guarantee for yours, so check your own.

One trap in that check: nccl-tests' `-c N` compares N all-reduces per size *after* the timed loop, not every timed iteration. My first "one-hour soak" compared far fewer results than I thought it had. Set `-c` high and count what was actually compared.

Symmetric kernels (`-R 2` in nccl-tests, NCCL 2.27 and later) didn't help: they need an NVLink clique, PCIe peer-to-peer isn't one, and they never engaged. Nor did more channels and cross-NIC rings, which spread large messages over two NICs per host but did nothing at decode sizes.

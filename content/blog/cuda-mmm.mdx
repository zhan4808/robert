SGEMM is probably the most important kernel in modern deep learning. If you could only profile one operation in a transformer, this would be the one. I wanted to understand from first principles why GPUs are so good at it, and what it takes to close the gap with cuBLAS. This post is my attempt to work through that one step at a time, starting from a naive kernel and ending at \~94% of cuBLAS on an A6000.

What I like about this exercise is that the naive implementation is about 75x slower than cuBLAS, and almost none of that gap is algorithmic. It comes from understanding the memory hierarchy and keeping the compute units fed. The math is simple. Moving the data is the hard part.

First, some background. CUDA organizes computation into a three-level hierarchy. A kernel launch creates a grid of blocks, each block contains up to 1024 threads, and threads within the same block share a fast on-chip scratchpad called shared memory (SMEM). The hierarchy exists mostly so it can map onto the hardware: blocks run on streaming multiprocessors (SMs), and threads within a block share that SM's SMEM.

The blockDim variable is a 3D integer vector specifying how many threads live in each block dimension. Combined with gridDim (the number of blocks), this determines the full thread layout:

/>

It took me a while to internalize that the thread hierarchy is mostly about correctness. For performance you have to think in warps, which are groups of 32 threads that execute in lockstep. The block/grid structure tells you who can communicate. The warp structure tells you what the hardware schedules.

## Kernel 1: Naive Implementation

The simplest kernel assigns each thread one output element of C and loops over the K dimension to accumulate the dot product. As you'd expect, it's slow. Each thread reads a full row of A and a full column of B on its own, and there's almost no data reuse between threads.

<Figure
  src="/cuda-mmm/naive-kernel.webp"
  alt="Naive kernel visualization showing thread layout and computation assignments"
  caption="Each thread computes exactly one output entry of C."
  invert
/>

```cpp
__global__ void sgemm_naive(int M, int N, int K, float alpha, const float *A,
                            const float *B, float beta, float *C) {
  const uint x = blockIdx.x * blockDim.x + threadIdx.x;
  const uint y = blockIdx.y * blockDim.y + threadIdx.y;

  if (x < M && y < N) {
    float tmp = 0.0;
    for (int i = 0; i < K; ++i) {
      tmp += A[x * K + i] * B[i * N + y];
    }
    C[x * N + y] = alpha * tmp + beta * C[x * N + y];
  }
}
```

CUDA kernels are written from the point of view of a single thread. You describe what one thread does, and the runtime stamps out N copies of it across the grid. The blockIdx and threadIdx builtins tell each thread where it sits, and the global index always follows the same pattern: blockIdx \* blockDim + threadIdx.

If the matrix dimension isn't divisible by BLOCKSIZE, you have to launch extra blocks to cover the remainder, and some of their threads sit idle (tile quantization). The overhead is small for large matrices but shows up at small sizes, which is part of why cuBLAS picks different kernels depending on the matrix dimensions.

### Napkin Math: How Fast Can This Be?

Before profiling anything, I wanted a bound. For two 4092² matrices, the GEMM requires 2×4092³ ≈ 137 GFLOPs. The minimum GMEM transfer is 268MB (3 matrices × 4092² × 4B). On an A6000 with 30 TFLOPs/s of compute and 768 GB/s of bandwidth, the compute takes \~4.5ms and the memory traffic takes \~0.34ms. Since compute dominates by \~13x, the kernel should be compute-bound once we stop wasting bandwidth. cuBLAS itself loads about 500MB during the computation (more than the theoretical minimum), and that's the number to beat.

I kept this ratio in mind through every optimization. At each step the question is whether we've moved closer to being compute-bound or are still wasting bandwidth. The roofline model makes that explicit.

### Why the Naive Kernel is Terrible

Two threads in the same block with threadIds (0,0) and (0,1) load the same column of B but different rows of A. With no caching, each thread loads 2×4092 floats, so 4092² threads produce 548GB of memory traffic for a 268MB problem. That's a 2× overshoot even in theory, and much worse in practice because threads share nothing.

  caption="Memory access pattern of the naive kernel for two example threads (red and green)."

/>

Result: \~300 GFLOPs on an A6000. For context, a well-tuned 2015 Haswell CPU gets about that. A GPU with 100× the memory bandwidth performs like a CPU because we're ignoring how it wants memory to be accessed.

## Kernel 2: Global Memory Coalescing

This kernel is about warps. Threads within a block are grouped into warps of 32, and the warp is the unit of execution on the hardware: all 32 threads execute the same instruction at the same time (SIMT). The warp scheduler is what dispatches instructions to the CUDA cores.

Warps are formed from consecutive threadIds: threadId = threadIdx.x + blockDim.x\*(threadIdx.y + blockDim.y\*threadIdx.z). The x dimension is the fast-varying one. I think of it as column-major in 'warp space': threads with adjacent threadIdx.x values end up in the same warp.

<Figure
  src="/cuda-mmm/threadId_to_warp_mapping.webp"
  alt="Illustration of how threadIds map to warps"
  caption="Thread-to-warp mapping illustrated using an 8-thread warp example (real warps have 32 threads)."
  invert
/>

Global memory coalescing is the most important GMEM optimization on a GPU. When threads in the same warp request consecutive addresses, the hardware combines them into one transaction. 32 threads × 4 bytes = 128 bytes, exactly one L2 cache line, so perfect coalescing means 1 transaction per warp instead of 32.

<Figure
  src="/cuda-mmm/GMEM_coalescing.webp"
  alt="Consecutive memory accesses grouped into single transactions"
  caption="Global memory coalescing groups consecutive warp accesses into fewer, larger transactions."
  invert
/>

Threads within a warp don't have to access memory in threadIdx order for this to work. They only need to collectively touch a consecutive, aligned 128B region, and the hardware decides which transaction to issue from the union of the addresses. So a scrambled access pattern within a warp still coalesces as long as the addresses are contiguous.

<Figure
  src="/cuda-mmm/random_access_coalescing.webp"
  alt="Non-consecutive within-warp accesses that still coalesce"
  caption="Non-consecutive within-warp accesses can still coalesce as long as they target consecutive addresses."
  invert
/>

In the naive kernel we mapped threadIdx.x to the row of A. Threads with consecutive threadIdx.x (i.e., in the same warp) therefore load consecutive rows of A. But A is row-major, so consecutive rows are K floats apart. That's 32 × K × 4B of cache-line fetches for K dot-product steps, with no coalescing at all.

<Figure
  src="/cuda-mmm/Naive_kernel_mem_coalescing.webp"
  alt="Non-consecutive row loading from matrix A in naive kernel"
  caption="The naive kernel accesses A non-consecutively, preventing coalescing."
  invert
/>

The fix is to swap how output elements are assigned to threads: threadIdx.x → column instead of threadIdx.x → row. Threads in the same warp now compute the same row of C but consecutive columns, so they load the same row of A (a broadcast) and consecutive columns of B (coalesced).

<Figure
  src="/cuda-mmm/Naive_kernel_improved_access.webp"
  alt="Reorganized thread-to-result mapping for coalescing"
  caption="Reorganizing the thread-to-result mapping enables coalesced global memory access."
  invert
/>

This only changes the first two lines of the index computation:

```cpp
const int x = blockIdx.x * BLOCKSIZE + (threadIdx.x / BLOCKSIZE);
const int y = blockIdx.y * BLOCKSIZE + (threadIdx.x % BLOCKSIZE);

if (x < M && y < N) {
  float tmp = 0.0;
  for (int i = 0; i < K; ++i) {
    tmp += A[x * K + i] * B[i * N + y];
  }
  C[x * N + y] = alpha * tmp + beta * C[x * N + y];
}
```

One thing surprised me: enabling coalescing doesn't change a single assembly instruction. The memory system handles it at runtime, and the PTX and SASS are identical. In hindsight that makes sense. The compiler can't know whether the base pointers will be aligned, so it has no reason to emit different code, and the hardware works it out per transaction.

The payoff is large. Memory throughput goes from 15 GB/s to 110 GB/s, and FLOP/s from \~300 to \~2000 GFLOPS. The math is unchanged and there's still no shared memory; only the index assignment moved.

## Kernel 3: Shared Memory Cache-Blocking

Between registers and DRAM sits shared memory (SMEM). It's on-chip, physically next to the CUDA cores, and partitioned among blocks, so every thread in a block can read and write the same SMEM region. On Volta-era hardware SMEM bandwidth has been measured at \~12 TB/s, against \~750 GB/s for DRAM, roughly a 16× difference. On an A6000, each block gets up to 48KB of SMEM.

<Figure
  src="/cuda-mmm/memory-hierarchy-in-gpus.webp"
  alt="GPU memory hierarchy showing cache structure for A100"
  caption="The GPU memory hierarchy. Shared memory is on-chip and orders of magnitude faster than DRAM."
  invert
/>

With cache-blocking, threads stop fetching from GMEM independently. Instead, the block cooperatively loads a tile of A and a tile of B into SMEM, and then everyone computes on that local copy. The tile slides along the K dimension while threads accumulate partial sums. Since each float in SMEM is used by several threads, GMEM traffic per FLOP drops a lot.

<Figure
  src="/cuda-mmm/cache-blocking.webp"
  alt="Cache-blocking visualization showing chunk-based loading and computation"
  caption="Cache-blocking: load tiles of A and B into shared memory, compute partial sums, then advance."
  invert
/>

```cpp
A += cRow * BLOCKSIZE * K;
B += cCol * BLOCKSIZE;
C += cRow * BLOCKSIZE * N + cCol * BLOCKSIZE;

float tmp = 0.0;
for (int bkIdx = 0; bkIdx < K; bkIdx += BLOCKSIZE) {
  As[threadRow * BLOCKSIZE + threadCol] = A[threadRow * K + threadCol];
  Bs[threadRow * BLOCKSIZE + threadCol] = B[threadRow * N + threadCol];

  __syncthreads();

  A += BLOCKSIZE;
  B += BLOCKSIZE * N;

  for (int dotIdx = 0; dotIdx < BLOCKSIZE; ++dotIdx) {
    tmp += As[threadRow * BLOCKSIZE + dotIdx] *
           Bs[dotIdx * BLOCKSIZE + threadCol];
  }
  __syncthreads();
}
C[threadRow * N + threadCol] =
    alpha * tmp + beta * C[threadRow * N + threadCol];
```

This gets \~2200 GFLOPS, only a 50% improvement, which felt small for the effort. Part of the reason is that Kernel 2 already had decent L1 hit rates after the access pattern change, so explicit SMEM tiling buys less than you'd hope. The roofline shows the bigger problem.

<Figure

  alt="Roofline analysis showing performance vs arithmetic intensity for Kernel 3"
  caption="Roofline plot for Kernel 3. We're far from the compute roofline; arithmetic intensity is the bottleneck."
  invert
/>

### The Roofline and the Arithmetic Intensity Problem

The roofline model plots achieved FLOPs/s against arithmetic intensity (FLOPs per byte of memory traffic). It has two limits: a horizontal line at peak compute (30 TFLOPs/s) and a diagonal line at peak memory bandwidth (768 GB/s × FLOPs/byte). Below the diagonal you're memory-bound; at the horizontal ceiling you're compute-bound. Kernel 3 sits far below both. Its arithmetic intensity is too low to be compute-bound, yet it isn't saturating bandwidth either. It's stalling on SMEM.

Occupancy at CHUNKSIZE=32 is \~66% (limited by thread count, not SMEM or registers), which isn't bad. The profiler is more revealing: the instruction mix is dominated by LDS (shared memory loads) rather than FMA, so most cycles go to fetching from SMEM instead of doing math. Each thread needs to compute more outputs per SMEM access, which means doing more of the work in registers to lower the ratio of loads to FMAs.

## Kernel 4: 1D Blocktiling for Calculating Multiple Results per Thread

Instead of one output element, each thread now computes a column of TM output elements and keeps TM partial sums in registers across the K-dimension loop. The loop order matters here. dotIdx (the position within the BK tile) becomes the outer of the two inner loops, and resIdx (which of the TM outputs) becomes the innermost. For each dotIdx we load one value of Bs into a register (Btmp) and reuse it for all TM multiply-accumulates: one SMEM load for TM FMAs.

<Figure
  src="/cuda-mmm/kernel_4_1D_blocktiling.webp"
  alt="1D blocktiling showing multiple results per thread computation pattern"
  caption="1D blocktiling: each thread computes a column of TM output elements, improving register reuse."
  invert
/>

```cpp
float threadResults[TM] = {0.0};

for (uint bkIdx = 0; bkIdx < K; bkIdx += BK) {
  As[innerRowA * BK + innerColA] = A[innerRowA * K + innerColA];
  Bs[innerRowB * BN + innerColB] = B[innerRowB * N + innerColB];
  __syncthreads();

  A += BK;
  B += BK * N;

  for (uint dotIdx = 0; dotIdx < BK; ++dotIdx) {
    float Btmp = Bs[dotIdx * BN + threadCol];
    for (uint resIdx = 0; resIdx < TM; ++resIdx) {
      threadResults[resIdx] +=
          As[(threadRow * TM + resIdx) * BK + dotIdx] * Btmp;
    }
  }
  __syncthreads();
}
```

### What the Compiler Does for You

Because TM is a template parameter, the compiler knows it at compile time, so it can unroll the inner resIdx loop and keep the threadResults array entirely in registers. It would do the Btmp caching on its own as well, since it can see that Bs\[dotIdx \* BN + threadCol] doesn't change across resIdx iterations and hoist it into a register. This is why I template the tile sizes. Without compile-time knowledge, the compiler has to be conservative.

<Figure
  src="/cuda-mmm/1d_warp_tiling.webp"
  alt="1D warp tiling benefits showing shared input advantage"
  caption="The benefit of 1D blocktiling: threads in the same warp share loads from Bs, amortizing SMEM traffic."
  invert
/>

Result: \~8,600 GFLOPs, a 4× jump from Kernel 3. The profiler agrees: MIO stall cycles (shared memory contention) drop sharply, and the bottleneck moves from waiting on SMEM to doing FMAs. This is still only 1D output tiling, though, and there's more to get.

## Kernel 5: Increasing Arithmetic Intensity via 2D Blocktiling

The next step is to extend the idea to 2D, with each thread computing a TM×TN output tile. The gain in arithmetic intensity is multiplicative. Instead of reusing one Bs value across TM rows, we reuse each regM value across TN columns and each regN value across TM rows. The inner loop becomes an outer product: load TM values from As into regM, load TN values from Bs into regN, compute the full TM×TN outer product, and accumulate into threadResults.

<Figure
  src="/cuda-mmm/raising_arith_inten.webp"
  alt="Arithmetic intensity explanation showing compute-to-bandwidth ratio improvement"
  caption="2D tiling raises arithmetic intensity by reusing loaded values across both row and column dimensions."
  invert
/>

<Figure
  src="/cuda-mmm/kernel_5_2D_blocktiling.webp"
  alt="2D blocktiling diagram with three loop levels"
  caption="2D blocktiling: each thread computes an 8×8 result tile using three nested loops."
  invert
/>

```cpp
float threadResults[TM * TN] = {0.0};
float regM[TM] = {0.0};
float regN[TN] = {0.0};

for (uint bkIdx = 0; bkIdx < K; bkIdx += BK) {
  for (uint loadOffset = 0; loadOffset < BM; loadOffset += strideA) {
    As[(innerRowA + loadOffset) * BK + innerColA] =
        A[(innerRowA + loadOffset) * K + innerColA];
  }
  for (uint loadOffset = 0; loadOffset < BK; loadOffset += strideB) {
    Bs[(innerRowB + loadOffset) * BN + innerColB] =
        B[(innerRowB + loadOffset) * N + innerColB];
  }
  __syncthreads();

  A += BK;
  B += BK * N;

  for (uint dotIdx = 0; dotIdx < BK; ++dotIdx) {
    for (uint i = 0; i < TM; ++i) {
      regM[i] = As[(threadRow * TM + i) * BK + dotIdx];
    }
    for (uint i = 0; i < TN; ++i) {
      regN[i] = Bs[dotIdx * BN + threadCol * TN + i];
    }
    for (uint resIdxM = 0; resIdxM < TM; ++resIdxM) {
      for (uint resIdxN = 0; resIdxN < TN; ++resIdxN) {
        threadResults[resIdxM * TN + resIdxN] +=
            regM[resIdxM] * regN[resIdxN];
      }
    }
  }
  __syncthreads();
}
```

<Figure

Result: \~16 TFLOPs, another 2×. GMEM accesses per output element drop to K/64 and SMEM accesses to K/4, and we're now close to the compute roofline. What's left of the gap to cuBLAS comes from vectorized loads (memory efficiency) and warp-level data locality, which Kernels 6 and 10 go after.

## Kernel 6: Vectorize SMEM and GMEM Accesses

This kernel combines two tricks. The first is vectorized GMEM loads: using float4 to load 128 bits (4 floats) per instruction turns LDG.E.32 into LDG.E.128. You have to promise the compiler that the pointer is 128-bit aligned with a reinterpret_cast, because it can't infer that from a generic float\* argument. The second is transposing As during the SMEM load, so the later SMEM reads along the column dimension are sequential and can use LDS.128 instead of strided scalar loads.

<Figure
  src="/cuda-mmm/kernel_6_As_transpose.webp"
  alt="Memory layout changes enabling vectorized SMEM loads for As"
  caption="Transposing As during the GMEM→SMEM transfer enables vectorized 128-bit SMEM loads."
  invert
/>

```cpp
float4 tmp =
    reinterpret_cast<float4 *>(&A[innerRowA * K + innerColA * 4])[0];
As[(innerColA * 4 + 0) * BM + innerRowA] = tmp.x;
As[(innerColA * 4 + 1) * BM + innerRowA] = tmp.y;
As[(innerColA * 4 + 2) * BM + innerRowA] = tmp.z;
As[(innerColA * 4 + 3) * BM + innerRowA] = tmp.w;

reinterpret_cast<float4 *>(&Bs[innerRowB * BN + innerColB * 4])[0] =
    reinterpret_cast<float4 *>(&B[innerRowB * N + innerColB * 4])[0];
__syncthreads();
```

The transpose is the subtle part. In Kernel 5, reading a column of As in the inner computation meant strided SMEM reads, which cause bank conflicts. Storing As transposed (column-major) when loading it makes the inner reads row-sequential, which avoids the bank conflicts and allows vectorized LDS.128. The extra work at load time is cheap next to what it saves during compute.

Performance: \~18,200 GFLOPs, about 500 GFLOP/s over Kernel 5. That's a real gain but not a dramatic one, since the easy wins are mostly gone. At this point the gap to cuBLAS comes from SMEM bank conflicts, the lack of double buffering (the GPU stalls on SMEM loads instead of overlapping compute and fetch), and the warp-level register locality that warptiling exploits.

## Kernel 9: Autotuning

By now the kernel has five template parameters: BM and BN for the shared memory tile, BK for the K-dimension tile, and TM and TN for the per-thread register tile. My initial guess (BM=BN=128, BK=8, TM=TN=8) is reasonable but unlikely to be optimal. Autotuning here is a grid search with validation. I wrote a bash script that sweeps sensible combinations, benchmarks each one, and picks the fastest.

The tricky part is keeping the search space honest. Not every combination is valid; vectorized SMEM loads, for instance, require BM\*BK to be divisible by 4\*NUM_THREADS. Of \~400 configurations, maybe 200 compile and produce correct results. Checking each against a reference keeps a fast but wrong kernel from winning.

On the A6000 the winner was BM=BN=128, BK=16, TM=TN=8, so only the K-tile changed. That alone took throughput from \~19 to \~20 TFLOPs, a \~5% gain. I can't fully explain *why* BK=16 beats BK=8 on this GPU. A larger BK loads more data per SMEM phase, which cuts the total number of GMEM loads, but it also raises register pressure and changes occupancy. Where that balance lands depends on the hardware and is hard to predict on paper. It's why production libraries like CUTLASS and cuDNN ship hundreds of kernel variants and pick one at runtime with a dispatcher. The hardware is too varied for a single 'best' configuration.

## Kernel 10: Warptiling

Kernel 10 adds a third level of tiling between blocktiling and threadtiling: warptiling. CUDA mostly hides this level from you. Warps never appear explicitly in your code, but the hardware is built around them. Every 32 threads form a warp that executes in lockstep, the warp ID is just threadIdx.x / 32, and the scheduler works in warps rather than threads.

<Figure
  src="/cuda-mmm/Loop_structure.webp"
  alt="Block, thread, and warp tiling nesting levels"
  caption="The three-level loop structure: block tiles → warp tiles → thread tiles."
  invert
/>

<Figure
  src="/cuda-mmm/WarpSchedulers.webp"
  alt="Four warp schedulers per multiprocessor diagram"
  caption="Each SM has four warp schedulers. Warptiling lets different warps run on different schedulers concurrently."
  invert
/>

Warps matter here for three reasons. They're the unit of scheduling: the A6000 has four warp schedulers per SM, so four warps can issue instructions each cycle, and a block with only one warp's worth of useful work at a time leaves 3/4 of that capacity idle. SMEM bank conflicts also happen at the warp level, since accesses from 32 threads to the same bank serialize. And recent GPUs have register file caches that speed up access to recently used registers, so having the threads of a warp work on adjacent data improves locality at the register level. With warptiling, the three levels of the memory hierarchy line up with the three levels of the compute hierarchy: GMEM → block, SMEM → warp, registers → thread.

<Figure
  src="/cuda-mmm/kernel_10_warp_tiling.webp"
  alt="Three-level tiling visualization for Kernel 10"
  caption="Kernel 10 warptiling: each warp computes a (WSUBN*WNITER) × (WSUBM*WMITER) chunk of C."
  invert
/>

```cpp
for (uint dotIdx = 0; dotIdx < BK; ++dotIdx) {
  for (uint wSubRowIdx = 0; wSubRowIdx < WMITER; ++wSubRowIdx) {
    for (uint i = 0; i < TM; ++i) {
      regM[wSubRowIdx * TM + i] =
          As[(dotIdx * BM) + warpRow * WM + wSubRowIdx * WSUBM +
             threadRowInWarp * TM + i];
    }
  }
  for (uint wSubColIdx = 0; wSubColIdx < WNITER; ++wSubColIdx) {
    for (uint i = 0; i < TN; ++i) {
      regN[wSubColIdx * TN + i] =
          Bs[(dotIdx * BN) + warpCol * WN + wSubColIdx * WSUBN +
             threadColInWarp * TN + i];
    }
  }

  for (uint wSubRowIdx = 0; wSubRowIdx < WMITER; ++wSubRowIdx) {
    for (uint wSubColIdx = 0; wSubColIdx < WNITER; ++wSubColIdx) {
      for (uint resIdxM = 0; resIdxM < TM; ++resIdxM) {
        for (uint resIdxN = 0; resIdxN < TN; ++resIdxN) {
          threadResults[(wSubRowIdx * TM + resIdxM) * (WNITER * TN) +
                        (wSubColIdx * TN) + resIdxN] +=
              regM[wSubRowIdx * TM + resIdxM] *
              regN[wSubColIdx * TN + resIdxN];
        }
      }
    }
  }
}
```

After autotuning kernel 10, throughput went from \~19.7 to \~21.7 TFLOPs, a 10% jump from warptiling alone. At large sizes the gap to cuBLAS is now small, maybe 5-10%. The chart below tells a different story for small matrices, where cuBLAS is far ahead. Using nvcc --generate-code to pick apart the cuBLAS binary shows why: it contains \~16 distinct SGEMM implementations and chooses one at runtime based on matrix shape and size. For small square matrices it uses a split-K variant that partitions the K-dimension across thread blocks, which exposes more parallelism when M and N are small. No single kernel is optimal at every shape, and cuBLAS doesn't try to be one.

## Conclusion

What surprised me most about this project was the shape of the progress curve more than any single optimization. The first two kernels (naive → coalesced) covered about 80% of the gap to cuBLAS and took maybe a weekend to understand and implement. The remaining 14% took weeks. Past the easy wins, each step needed more hardware knowledge, better instincts with the profiler, and more patience with results I couldn't fully explain.

Most of what SGEMM taught me carries over to other GPU work. Memory bandwidth is almost always the binding constraint, and each layer of the memory hierarchy (GMEM → L2 → SMEM → registers) exists to work around it at a smaller scale. The same loop shows up in nearly every fast GPU kernel: find the bottleneck, tile across the memory level that relieves it, and repeat. Attention kernels (FlashAttention), convolutions and sparse operations are all variations on it. Writing SGEMM from scratch is a good way to learn the vocabulary.

One thing I'd add beyond the original: if you want to see why cuBLAS is so hard to beat, look at your kernel's warp efficiency, memory throughput and SM occupancy in the profiler at the same time. They often pull against each other. Raising occupancy can hurt register reuse, and bigger tiles can hurt occupancy. CUTLASS, with its hierarchical policies and autotuned dispatch, is a systematic answer to that tradeoff. For production ML infrastructure I'd build on CUTLASS. For learning, there's no substitute for writing the kernels yourself.
